Notes on the deposited code and data of ISLE

An independent code & data audit by Natural Joints.

Re: Lee, J.S. et al. “Harnessing synthetic lethality to predict the response to cancer treatment.” Nature Communications 9, 2546 (2018). DOI 10.1038/s41467-018-04647-1. Repository: github.com/jooslee/ISLE.

To: the authors of ISLE.

Constructive reproducibility review 3 observations Public artifacts only

Purpose. A constructive, reproducibility-oriented review of the publicly deposited artifacts. We report three observations and, in each case, request a clarification or suggest a small fix. None questions the central biological hypothesis: one concerns the provenance of the deposited drug network, one is most likely a column-labeling/wording matter, and one is a small annotation correction. Where a conclusion would depend on code that is not in the repository, we say so explicitly rather than assert an effect on the published results.

1 · Methodology of this review

We worked only from public materials: the GitHub repository — the R pipeline (R/isle.r, R/isle.pairs.r, R/isle.drug.r), the C++ kernels (src/*.cpp), the bundled data/*.RData, and the three Cytoscape networks (networks/*.cys); the published article and Supplementary Information; the 14 Supplementary Data tables; and the article’s peer-review file.

Our procedure:

  1. Static + dynamic code read. We read the three pipeline scripts and the C++ kernels and re-ran the runnable portions in R (R 4.x) against the deposited data/*.RData.
  2. Output recovery. We parsed the deposited Cytoscape sessions (the XGMML inside each .cys) to recover the exact node and edge sets of the published networks.
  3. Supplementary-table integrity. We profiled the 14 tables (Python/pandas) for count consistency, value ranges, duplicates, and label coherence.
  4. Claim ↔ artifact cross-referencing. We lined up statements in the Methods/SI against the code’s behavior and against the deposited outputs.
  5. Independent semantic profiling. We ran an automated column-semantics / data-quality pass over the supplementary tables as a second, independent check.

Every observation below was verified by re-running code and — where possible — cross-validated against the deposited network output, not only against the source code.

2 · What we were and were not able to audit

Auditable (and audited): the network-identification code; the bundled cell-line / essentiality screens and other data/*.RData; the deposited cSL networks (the published results of record); the supplementary tables; the paper / SI / peer-review text.

Not auditable from the public artifacts:

  • Steps I–II of the pipeline could not be re-run. Both isle.r and isle.drug.r begin with load("data/prob.TCGA.RData"), but that file is not in the repository and the documented source (ftp://ftp.umiacs.umd.edu/pub/jooslee/prob.TCGA.RData) is no longer reachable — also the subject of the repository’s open issue #1.
  • The headline performance numbers could not be reproduced. The repository contains the network-identification code only; the prediction/evaluation code that produces the cSL-score, ROC/AUC, Kaplan–Meier and C-index results is not deposited.

We therefore confined ourselves to what is provable from the deposited code, the deposited network outputs, and the published text, and we flag explicitly where a conclusion would require the unreleased prediction code.

For balance, several things we checked held up well, and we note them so the three findings are read in context: the C++ statistical kernels (HyperGeometricTest.pair.cpp, essentialityTestPair.cpp) are correctly specified; and we found no circularity in the survival analysis — the cSL network is selected on TCGA survival but validated on the independent METABRIC and GSE25055 cohorts, which is appropriate.

3 · Findings

Finding 1 — The deposited drug-network pipeline does not appear to incorporate Initial Set I (the gold-standard SL set)

substantive · provenance

Observation. In R/isle.drug.r (line 69) and R/isle.pairs.r (line 22), the gold-standard set is read as gd$sl:

gd$sr = gd$sl[gd$flag==1,]

The deposited object gd in data/sl.golden.set.RData has fields sr, sr0, flag, dat — there is no $sl. (For comparison, R/isle.r line 75 reads gd$sr and is unaffected.) As a consequence, the gold-pair injection that should force the curated pairs through Step 0 — the block that sets p.ess[iix] = 1e-6 so Initial Set I survives the essentiality gate — receives zero pairs. The mechanism is subtle: the failed assignment removes the sr element, after which gd$sr partial-matches the remaining gd$sr0 and returns the gold pairs as gene symbols, whereas the drug candidate pool is built from integer gene indices; the subsequent match(...) therefore returns 0 of 12,066.

Cross-validation against the deposited output. This is not only a source-code observation. The deposited drug network (networks/ISLE_drug_cSL_network.cys: 232 edges, 16 drug nodes — matching the paper) contains none of the 6,033 gold-standard pairs as edges. For the drug-target hub genes that are themselves gold-standard genes, none of their curated SL partners appear among their network neighbors (e.g. TOP1: 43 gold partners, 0 present; ERBB2: 22, 0). Had the injection run, those partners would have been forced through Step 0 and should dominate those neighborhoods; their complete absence indicates the injection did not run when the deposited network was produced.

Implication and what we cannot determine. The Methods describe the candidate pool as Initial Set I (gold standard) ∪ Initial Set II (inferred). For the drug-target network as deposited, Set I appears not to have contributed. We cannot determine whether (a) the published analysis used a different, unreleased gold-standard file/variable in which the field was named sl, or (b) the deposited drug network was in fact built from Set II only. Either way, the deposited code and the deposited network are mutually consistent in omitting Set I, so the discrepancy is with the described method rather than an artifact of our re-run.

RequestCould you confirm which gold-standard file/variable the published drug network used? If it differs from the deposited sl.golden.set.RData, depositing that version would resolve this immediately. If the drug network was intentionally built without Set I, a note to that effect would reconcile the code with the Methods.
Suggested fixUse gd$sr, and ensure the gold pairs are mapped into the same integer-index space as the candidate pool before match(...).

Finding 2 — The “% Growth inhibition” columns in Supplementary Data 7 and 8 appear to contain % viability

most likely a labeling / wording matter · results unaffected

Observation. Several independent signals indicate that the SD7 and SD8 columns headed “% Growth inhibition” actually contain cell viability (the complement of inhibition):

  • potent cytotoxics sit near 0 (Tamoxifen 0.1, Doxorubicin 1.3, Docetaxel 8.2, Topotecan 6.2), while non-cytotoxic compounds sit near 100 (Citalopram 98, Allopurinol 102, Ibuprofen 100);
  • a large fraction of values exceed 100 (≈48% in SD7, ≈15% in SD8; max ≈ 152) — implausible for “% inhibition,” but expected for viability (proliferation above control);
  • the assay is described as quantifying stained-nuclei counts, which is a viability readout;
  • Spearman(column, established drug potency) ≈ −0.857.

Why we believe this is most likely a labeling/wording issue and not a results problem. Read literally, the Methods define responders as “top 33% of observed growth inhibition = effective.” If that rule were applied to these columns as deposited, the responder set would be the highest-viability (least active) compounds, and — because the cSL-score increases with predicted efficacy — the predictor would anti-correlate with the labels, yielding AUC < 0.5. The paper instead reports AUC ≈ 0.73–0.75. An inverted pipeline cannot produce AUC > 0.5, so the reported results indicate the analysis used the correct orientation. We therefore believe the discrepancy is confined to the column header (and the corresponding Methods phrasing) in the deposited artifacts, and that the published numbers are unaffected. We were unable to confirm this directly only because the responder-labeling / prediction code is not deposited.

RequestCould you confirm that the deposited SD7/SD8 values are viability, in which case the header and the Methods sentence would read “% viability” (or the values should be reported as 100 − x)? Depositing the few lines that derive the responder labels from these columns would close the question conclusively.
Suggested fixRelabel the columns as “% viability” (or transform to 100 − x) and align the Methods wording.

Finding 3 — A few drug→target annotations in Supplementary Data 13 appear incorrect

minor · bounded · no headline drug affected

Observation. Several mappings in SD13 do not match the listed drugs’ established pharmacology, e.g. Dacarbazine→PGD and Lomustine→STMN4 (both DNA-alkylating agents whose listed targets are unrelated to their mechanism); Carmustine→GSR as the sole target (a secondary effect); Bleomycin→LIG1/LIG3; and Epirubicin→CHD1/TOP2A (TOP2A is correct; CHD1 is questionable).

Effect — and why it is small. Because a drug’s cSL-score is computed from its targets’ SL partners, an incorrect target causes that specific drug’s prediction to reflect the wrong gene’s biology. The effect on the paper is bounded:

  • Of the questionable mappings, only Dacarbazine→PGD and Epirubicin→CHD1 are live edges in the deposited drug network; the others (Lomustine, Carmustine, Bleomycin) were pruned and contribute nothing to any output.
  • Epirubicin remains partly anchored by the correct TOP2A, so its score is diluted rather than wrong; that leaves Dacarbazine as the only fully-incorrect live mapping.
  • Neither drug is among the headline validation drugs, and every reported metric is an aggregate over many drugs, so the contribution to any AUC / hit-rate is at most ~1/N. No stated conclusion depends on these drugs.
Request / suggested fixPlease review and correct the SD13 annotations — in particular Dacarbazine and Epirubicin — ideally against a standard drug-target reference (e.g. DrugBank).
